# Oyster OTC — Prod Pre-Launch Checklist

This document captures everything that must be rotated, accepted, or replaced
before Oyster goes live for real users.

The current prod stand-up was driven by an agent (Claude Code) for an
operator-only controlled test. Every key listed below is currently held by the
agent / sits in cleartext in AWS Secrets Manager. Before product launch, each
of these items must be replaced or escalated.

## Critical — must be done before any external user touches prod

### 1. Rotate the Base mainnet deployer / initial-owner privkey

- **Where:** AWS Secrets Manager `prod/oyster-otc-base-deployer` (us-east-1).
- **What it controls:** Currently the `owner()` of the `PrlUsdcEscrow` contract
  at `0x5E3cca8Fc360C9dC28AE28CF65fd073e940Ec375` until ownership acceptance.
  The owner can call `release()` on every funded escrow, pause/unpause the
  contract, and change the fee recipient.
- **Action:** Once the new owner accepts ownership (see item 2 below), drain
  this wallet of any remaining ETH on Base and rotate the privkey out of SM
  (or delete the secret entirely).

### 2. Accept ownership on the Base mainnet escrow contract

- **Pending tx:** `acceptOwnership()` from
  `0x35C76bF5A701A30629d9706F4c8f77a4a0cA5978` (the address the deployer queued
  via `transferOwnership`).
- **Why it matters:** Until this is called the deployer remains the owner.
  Production launch should not happen with an agent-generated key as the
  contract owner.
- **Action:** Sione (or whoever controls `0x35C76bF…`) signs `acceptOwnership()`
  on Base mainnet. Record the tx hash in
  `contracts/usdc-escrow/deployments/base-mainnet.json`.

### 3. Rotate the prod arbiter privkey

- **Where:** AWS Secrets Manager `prod/oyster-otc-signer` (us-east-1), key
  `OYSTER_WORKER_ARBITER_PRIVKEY_HEX`.
- **What it controls:** Co-signer authority on every multisig OTC trade that
  opted in to `preauthorize_release`. With this key plus the stored buyer
  pre-signature, the worker can complete the `buyer_arbiter_release` script
  path → spend the escrow's PRL to the buyer's Pearl address.
- **Current state:** Cleartext, IAM-restricted to the prod worker role only.
  Acceptable for low-cap operator-only testing; **not** acceptable for live
  user traffic.
- **Action:**
  1. Generate the new arbiter key with appropriate ceremony (HSM, KMS-backed,
     or air-gapped — pick the model that matches the launch risk profile).
  2. Update the prod allocator config to use the new arbiter pubkey
     (`PEARL_ESCROW_ARBITER_PUBKEY` in `prod/oyster-otc-api`).
  3. **Note:** rotating the arbiter pubkey invalidates every active multisig
     escrow allocated with the old pubkey — those escrows' addresses are
     committed to the old key. Trades in flight at rotation time will need
     manual resolution. Best done during a maintenance window with no active
     trades.
  4. Replace `OYSTER_WORKER_ARBITER_PRIVKEY_HEX` in `prod/oyster-otc-signer`.

### 4. Replace `prod/oyster-otc-api` synthetic secrets

The following keys in `prod/oyster-otc-api` were generated by the agent during
stand-up and should be reviewed/replaced:

| Key | Current value | Action |
|---|---|---|
| `OTC_API_DATABASE_URL` | Points at `oyster_otc_api` role in `postgres-prod` RDS with an agent-generated password | Optional: rotate the role password if you want fresh credentials. Leave as-is if acceptable. |

## Operational hardening — should be done before scale

### 5. Postgres-backed broadcast-attempts ledger

The settlement-worker currently persists Pearl release broadcast attempts to a
JSON file in an `emptyDir` mount. Single replica only, no PVC. Pod restart
loses the ledger; redundant signatures are recovered via deterministic
re-signing + Pearl RPC's `tx already exists` rejection, but this is brittle.

**Action:** Add a Postgres-backed `PearlEscrowBroadcastAttemptRepository`
implementation in `services/settlement-worker/src/`, migrate the worker to use
it, and replace the `emptyDir` with no persistence. Document in the deployment
runbook. Enables horizontal scaling and survives reorgs.

### 6. EVM auto-broadcaster for Base release

Right now the worker emits a `prepare_usdc_release` decision but does not call
`Escrow.release(tradeKey)` on Base — an operator does it manually. Fine for
controlled testing; unsustainable for production volume.

**Action:** Add an Ethers-based broadcaster adapter that signs `release()` with
the contract owner key (or via Safe + Gnosis SDK) and submits to Base. The
owner key handling rides on the same custody decision as the arbiter privkey.

### 7. Real operator identity / RBAC for the admin surface

The admin routes today gate on bearer tokens. There's a multi-token
compatibility layer (`OTC_ADMIN_API_TOKENS` carries one token per role) but no
real identity, no audit-tied actor, no rotation, no SSO.

**Action:** Wire up the OTC admin API behind real auth before broader support
team rollout (referenced as task `9.9.1` in
`docs/openspec/pearl-infra-ecosystem/tasks.md`).

### 8. Lock the custody policy formally

Document the chosen custody model for prod — coordinator-P2TR vs true 2-of-3
multisig — in `docs/operations/bridge-reserve-custody-policy.md` (or a peer
document for OTC custody). Explicit on signer identities, cap limits,
emergency-pause authority, recovery plan.

### 9. Acknowledge known dev-time trade-offs that carried into prod

These are documented in `docs/operations/oyster-dev-testing.md` but worth
re-flagging here since prod inherited them:

- Worker doesn't write `pearl_release` side-effects into Postgres on broadcast;
  trade proof catches up via the Pearl indexer's observed spend.
- Trade state updates are not optimistic-concurrency-guarded (cross-cutting
  repo concern).
- No exponential backoff on failed Pearl broadcast retries.
